> 先理解这笔生意，才看得懂表结构与统计口径。

## 是什么

**保函（Guarantee）**是银行或担保机构应申请人请求，向受益人出具的书面承诺：
若申请人未履行约定义务，由出具方按约定金额赔付。平台处理两类：

| 类型 | 英文 / 表 | 场景 | 金额口径 |
| --- | --- | --- | --- |
| **投标保函** | tender guarantee / `tender_order` | 投标人参与招标时，向招标方保证「中标后会签约、不会撤标」 | 项目额的 **4%–14%** |
| **履约保函** | performance guarantee / `performance_order` | 中标后，向招标方保证「会按合同履约」 | 项目额的 **8%–25%** |

三笔关键金额：

```text
保额（guaranteeAmount）  = 平台对外承诺赔付的上限
保费（premiumAmount）    = 保额 × 费率     ← 平台的实际收入
项目额                    = 保函金额的计费基数
```

**保费才是收入**，保额是风险敞口。统计时把两者混起来是常见错误。

## 领域对象与关系

```text
sys_org（机构，20 个）
   └── sys_department（部门，树形：机构 → 部门 → 子部门）
          └── sys_user（用户，300 个）──> sys_role ──> sys_permission

sys_region（地区字典：省 / 市 / 区）  ← 订单按区域统计
insurance_type（险种，6 个）          ← 订单按险种统计
enterprise（企业，3000 个）           ← 订单的申请主体
project（项目，5000 个）              ← 保函对应的工程项目
   └── tender_order / performance_order（10 万 + 5 万）
```

机构与部门是**运营组织维度**（谁负责这笔业务），
企业是**客户维度**，项目是**业务标的维度** —— 三者不要混。

## 为什么重要

- **统计口径的正确性依赖对领域对象的理解**。
  例如「去重企业数」在 `orderType=ALL` 时必须对两张订单表 `UNION ALL` 后再
  `COUNT(DISTINCT)`，否则同一企业同时有投标与履约订单会被算两次。
- **筛选下拉的选项口径与授权口径是两个不同的问题**：
  「这个用户能看到哪些机构 / 险种的可选项」取决于其数据范围，
  见 `docs/DEC-业务筛选下拉的授权口径.md` 与 `docs/DEC-订单筛选下拉的选项口径.md`。
- 用户的**机构归属概念已被移除**（见 `docs/PLAN-移除用户与部门的机构归属.md`），
  若看到旧代码或旧文档提到「用户的机构」，那是过期信息。

## 怎么用 / 关键细节

回答业务问题时需要同时确认三件事，缺一不可：

```text
1. 时间范围     → 明确日期区间（不要用「本季度」这种相对说法，除非已解析）
2. 订单类型     TENDER / PERFORMANCE / ALL（也接受中文「投标」「履约」）
3. 数据范围     当前用户有权看哪些机构 / 区域的数据
```

三条都明确后，统计结果才具备可比性。
AI 侧由 `TimeSemanticParser` + `AiDataScopeResolver` 分别负责第 1 与第 3 条。

## 坑 / 限制

- 演示数据的业务规律是**人为注入**的，不代表真实市场，见
  [[技术 - 演示数据与可验证业务规律]]。
- `orderType=ALL` 的聚合比单类型慢（要做 `UNION ALL`），但**口径才正确**，
  不要为了性能改成分别统计再相加。
- 保费与保额不要混用。
