# 决策 - 采用模块化单体而非微服务

### decision

平台采用**模块化单体（Modular Monolith）**：一个 Spring 上下文聚合 7 个 Maven 模块，
不引入微服务、不引入 MQ 做服务间通信。模块边界靠**单向无环的 Maven 依赖**保证。

### why

- 本阶段的真实瓶颈是**业务功能与 AI 能力**，不是服务治理。微服务要付出的
  分布式事务、服务发现、链路追踪、部署编排成本，在这个阶段换不到对应收益。
- 但「单体」不等于「没有边界」：用 Maven 模块 + 单向依赖把边界固定下来，
  将来真要拆，拆分点已经清晰（图纸已经画好了）。
- 一个进程意味着本地开发只需起 MySQL + Redis，AI 工具调用也不需要跨进程调用业务 Service，
  链路短、易调试、易测试（`AiToolChainIT` 能在单进程内验证完整 Tool 链路）。

### context

项目定位是「传统电子保函管理后台 + AI 基础能力」的第一阶段。
团队规模与部署规模都不需要微服务。README 明确记载：本阶段**未实现** MCP、RAG、
Vector DB、Agent Planner、Memory、多模型路由、LangChain4j、MQ —— 这些都被有意推迟。

### alternatives

- **微服务拆分** —— 运维与分布式复杂度远超本阶段收益；且会让「AI 工具调用业务 Service」
  变成跨服务调用，链路与事务都变复杂
- **纯单模块（不分 Maven 模块）** —— 边界完全靠约定，代码量上来后必然腐化；
  模块化单体的成本几乎为零，却把边界变成编译期约束
- **模块化单体 + MQ 做模块间解耦** —— 引入最终一致性，与「统计口径唯一、结果可交叉验证」
  的目标冲突（异步会让「AI 答案」与「页面统计」出现时间差）

### constraints

- 依赖必须**单向无环**：`common` 不依赖任何业务模块
- `CurrentUser` 必须放在 `common`（否则 `ai`/`analysis` 要反向依赖 `auth`，形成环）
- 不得为了绕过边界而在下游模块直接引用上游模块的 Mapper
- 部署形态保持单进程 jar（后端同时承载 `frontend/dist`）

### consequences

**正面**

- 本地开发只需 MySQL + Redis 两个进程，没有服务编排
- AI 工具调用在同进程内完成，链路短、可精确计时、可确定性测试
- 统计口径只有一处实现，页面与 AI 结果天然一致
- 模块边界是编译期约束，不需要靠 review 记忆

**负面**

- 边界只有编译期约束，**没有运行期隔离**：绕过边界（如下游直接用上游 Mapper）
  技术上做得到，只能靠规范与 review 拦
- 单进程意味着一个模块的严重故障（如内存泄漏）影响全站
- 所有模块共享同一个发布节奏，无法按模块独立上线
- 将来若真要拆服务，仍需处理数据拆分与分布式事务（只是边界已清晰）

### revisitConditions

- 当某个模块（最可能是 `ai`）出现独立的扩缩容需求时
- 当构建时间或测试时间成为团队日常瓶颈时
- 当需要按模块独立部署以隔离故障时
- 当出现必须跨团队并行开发、且共享发布节奏不可接受时
