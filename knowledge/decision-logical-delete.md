# 决策 - 全表逻辑删除设计

### decision

所有业务表统一采用逻辑删除：新增 `is_deleted` / `deleted_at` / `deleted_by` 三列；
`status`（能力状态）与 `is_deleted`（存在状态）作为**两个正交维度**，删除**不隐式修改 `status`**；
唯一键改为函数索引 `(业务键, IFNULL(deleted_at, '1970-01-01 00:00:00.000000'))`。

### why

- 运营系统需要「删除错了能查、能恢复」，物理删除会让审计与数据修复无从下手。
- 但「删除」与「停用」是**两个不同的问题**：停用是「暂时不让它参与业务」（可逆、常发生），
  删除是「这条记录不再使用」。把两者塞进一个 `status` 字段会导致语义混乱：
  恢复时无法还原删除前的启用/停用状态，用户会觉得「恢复回来的和删之前不一样」。
- 唯一键必须同时满足两条互相冲突的诉求：**同一业务键只能有一条有效行**，
  以及**删除后业务键可被复用**。裸的 `(业务键, deleted_at)` 做不到 ——
  MySQL 唯一索引不约束 `NULL`，而 `deleted_at` 对未删除行正是 `NULL`，
  于是可以插入任意多条同业务键的有效行，漏洞没堵住。

### context

平台已有 18 张业务表在跑，且前端 5 个系统管理页面（机构 / 部门 / 用户 / 角色 / 险种）
都已有删除入口。此时改造逻辑删除，影响面覆盖：

- `guarantee-web`（schema / DataInitializer）
- `guarantee-system` / `guarantee-order` / `guarantee-analysis` / `guarantee-ai`（全模块 Mapper）
- `frontend`（删除入口、已删除标记）

设计文档 `docs/DEC-逻辑删除设计方案.md` 迭代到 **v2.2**，正是因为 v2.1 的裸唯一键方案
在评审中被发现存在「放行重复有效行」的缺陷。评审结论还有两条绝对禁止项：
不引入存储过程 / 触发器 / 函数；不改主键为雪花 ID。

### alternatives

- **物理删除** —— 无法审计、无法恢复，运营场景不可接受
- **只加 `is_deleted`，唯一键不动** —— 删除后业务键（订单号、机构编码、用户名）永久占用，
  新业务无法复用，且历史删除记录会与有效记录冲突
- **裸 `(业务键, deleted_at)` 唯一键（v2.1 方案）** —— 缺陷如上：MySQL 不约束 `NULL`，
  同一业务键可以有多条 `deleted_at IS NULL` 的有效行
- **把「删除」并入 `status`（三态：启用 / 停用 / 已删除）** —— 违反正交性，
  恢复时无法还原删除前的状态
- **触发器或存储过程统一维护** —— 被评审明确禁止（LD-EX-02）：逻辑会藏在数据库里，
  应用侧不可见、不可测、不可移植

### constraints

- 绝对禁止存储过程 / 触发器 / 函数
- 主键保持原样，不改成雪花 ID（LD-Q11）
- `ai_operation_secret` 为唯一例外：**不加**逻辑删除字段（它保存提案中的敏感信息，有独立清理路径）
- 改造期间必须保持既有 93 项测试全绿，改造后要能回归通过
- 必须能以 SQL 迁移脚本形式交付，便于在既有库上执行

### consequences

**正面**

- 删除可审计（`deleted_by` 能区分「业务用户删除」与「数据库直连删除」）
- 删除后业务键可复用，且「同一业务键只有一条有效行」被数据库唯一索引保证
- `status` 与 `is_deleted` 正交，恢复可完整还原删除前状态
- 停用前置检查只统计 `is_deleted=0` 的行，因此**已删除的用户不会继续阻塞部门停用**

**负面**

- 每条业务查询都**必须**记得加 `is_deleted = 0`，遗漏会静默返回已删除数据（易错点）
- 所有 Mapper 都要改，改造面极广（18 张表 + 13 个唯一键 + 全模块）
- 已交付后又发生一次推翻：前端「显示已删除」与「恢复」入口被全部撤除
  （后端接口与契约保留），因此**前后端能力不对称**，看代码时容易困惑
- 函数索引使唯一键可读性下降，排障时需要理解 `IFNULL` 哨兵的含义

### revisitConditions

- 当需要归档历史删除数据（例如把 `is_deleted=1` 且超过 N 年的行移到归档表）时
- 当 `is_deleted` 过滤遗漏成为真实线上缺陷、需要更强的机制（如视图或强制拦截）时
- 当 `ai_operation_secret` 也需要逻辑删除时（需重新评估它的例外地位）
- 当考虑改为分区表或独立历史表来承载删除记录时
