# 决策 - AI 写操作只产出提案

### decision

AI 的 WRITE 工具**只产出「操作提案」，绝不直接落库**。落库必须经用户在界面上确认后执行。
能力开关 `ai:system:write` 与各域权限是**「与」关系**：没有该开关时不注册任何 `propose*` 工具。

写操作固定流程：

```text
AI Plan → Permission Check → Preview → User Confirmation → Execute → Audit
```

### why

- 让模型直接改业务数据，一次幻觉就是一次数据事故，而且很难归因。
- 把「模型的意图」与「数据的变更」之间插入一个**人类确认点**，风险就从
  「不可控的自动写入」收敛为「可审计的显式动作」。
- 用户看到的是**预览**（将要改什么），而不是模型的事后描述 —— 确认的是事实，不是叙事。
- 能力开关与域权限分离，使「允许 AI 操作」可以独立于「用户本人能操作」被关掉，
  便于灰度与回退。

### context

第一阶段只上 READ 工具（`AiToolRegistry` 当时只注册 READ）。
随后需求要求补齐「系统管理」的操作能力，使 AI 助手与人工在页面上能做的事对齐
（`docs/REQ-系统管理助手能力.md`、`docs/REQ-系统管理手动操作能力补齐方案.md`）。
直接给模型写权限风险过高，因此引入提案机制：机构 / 部门 / 用户 / 角色 / 险种
各一个 `*ProposalTool` 与一个 `*ProposalExecutor`。

### alternatives

- **直接给 AI 写权限，用 Prompt 约束** —— Prompt 不是安全边界，模型可以忽略它；
  且失败时无法区分「模型判断错」与「执行出错」
- **完全不做写能力，只让用户手动改** —— 无法满足「能力对齐」需求，
  AI 助手的价值被限制在只读分析
- **AI 直接调用现有管理接口** —— 绕过了预览与确认，且会复用面向人的接口契约
  （含面向浏览器的分页、筛选语义），不适合模型调用
- **只记审计、不做确认** —— 事后审计无法阻止已经发生的错误写入

### constraints

- 写工具必须与读工具在权限上可分离（`ai:system:write` 独立开关）
- 预览必须来自真实的将要执行的动作，不能是模型生成的描述
- 敏感信息（如新建用户的初始密码）不得出现在普通会话/日志中，
  需独立存取（`ai_operation_secret`，**该表是唯一不加逻辑删除的表**）
- 提案必须防止被重复认领与重复执行
- 必须有失败记录与过期清理，否则会堆积

### consequences

**正面**

- 「AI 改数据」被收敛为可审计的显式动作，且审计里有 `trace_id` 可串起整条链路
- 模型幻觉最多造成一个**未被确认的提案**，不会直接污染业务数据
- 能力开关可独立关闭，回退成本低
- 提案本身成为可复盘的记录：模型想做什么、用户是否确认过

**负面**

- 用户体验多一步确认，流式对话的「一次问答完成」被打断
- 要维护提案的生命周期：创建、预览、认领、执行、失败、过期清理
  （`ProposalClaimGuard`、`ProposalFailureRecorder`、`ProposalMaintenanceJob`）
- 5 个域各一个 Tool + Executor，新增一个可写域的成本较高
- 敏感信息需要独立存储路径，增加了一张表与一套存取逻辑

### revisitConditions

- 当某类操作被证明「低风险且高频」，人工确认成为纯粹负担时（可考虑白名单式免确认）
- 当需要批量提案（一次提交多个变更）时
- 当需要把提案机制复用到非系统管理域（如订单）时
- 当 `ProposalMaintenanceJob` 的过期策略与真实使用节奏不匹配时
