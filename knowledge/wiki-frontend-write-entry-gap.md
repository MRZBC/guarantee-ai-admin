> 后端 CRUD 齐全、前端 API 封装也齐全，**但页面上没有接线** ——
> 表现为「按钮点不动」或「页面根本没入口」，最容易被误判成权限问题。

## 发生了什么

排查「机构的新增和修改，为什么超级管理员无法修改」时，真实原因不在权限、也不在后端：

```text
权限层   system:org:create / :update  → ADMIN_PERMISSIONS = 全部权限，超管有 ✅
后端     POST /api/system/orgs、PUT /api/system/orgs/{id} 已实现并带校验 ✅
前端     API createOrg / updateOrg 已定义且签名正确                    ✅
页面     Orgs.vue 渲染了占位的 <el-button disabled>修改</el-button>
        既没有 click 处理函数，也没有新增/编辑对话框              ❌ ← 真正的断点
```

`createOrg` / `updateOrg` 在整个 `frontend/src` 里**只有定义、零调用**。
所以"新增"连入口都没有，"修改"只有一个点不动的按钮。

**这个缺陷自己有编号**：设计文档把「页面有按钮但被禁用/占位，实际不可用」定义为 **V-2**，
把「后端有能力、页面上完全没有入口」定义为 **V-1**。两者经常成对出现。

## 为什么重要

- **它伪装成权限问题。** 按钮渲染出来（`v-if="canUpdate"` 为真 ⇒ 用户确实有权限），
  却因为 `disabled` 点不动。用户看到的结论必然是"我这个账号不能改机构"，
  而真实结论是"这个功能没做完"。项目文档对这条的措辞很准确：
  **一个渲染出来但点不动的按钮，比"没有按钮"更容易让人误判为"我没有权限"或"系统坏了"。**
- **它伪装成"已实现"。** 按功能清单对账时，后端接口 ✅ + 前端 API ✅ 很容易被记成已完成，
  于是这种缺口会在多轮 review 里被反复漏掉。
- **它无法被现有测试拦住。** 后端单测覆盖 `OrgService` 的校验（编码唯一、防环、数据范围），
  但没有任何测试断言"页面真的调用了 `updateOrg`"。`vue-tsc` 只保证类型正确，
  **未使用的导出函数不会报错**。

## 排查这种问题的顺序

```text
1. 先看按钮是 v-if 不渲染，还是渲染了但 disabled
   —— 不渲染 = 权限问题；渲染但 disabled = 几乎一定是没接线
2. 用 grep 验证"API 封装函数是否真的有调用点"
   —— 只有 export function 一处命中 = 零调用 = 页面没接
3. 去 docs/ 查这个模块有没有 V-1 / V-2 编号
   —— 有编号说明是已知待补项，直接照方案实施，不要重新设计
4. 最后才怀疑权限与后端
```

## 坑 / 限制

- **`disabled` 必须给出语义，否则就是 V-2 本身。** 项目的约定是
  `disabled` + `el-tooltip` + `<span>` 三件套，让用户能区分
  "我没权限""这是保留项""系统坏了"。**只有禁用而无说明 = V-2 未修复。**
- **前端无法自我校验这类缺口。** 前端没有单元测试框架，唯一的门禁是
  `vue-tsc --noEmit`（只查类型）与 `vite build`（只查能否打包）。
  判断"功能是否真的可用"目前只能靠人工点，或按文档逐条核对页面入口。
- **本项目的修法是"补页面"，不是"改后端"。** `OrgController` 的写接口、
  `OrgService.validateCreate/validateUpdate` 的校验都已就位且带单测，
  补页面时应当复用它，不要另起一套校验口径（违反「业务口径唯一实现」）。
