# 前端构建产物说明（chunk 拆分，R2 未闭环第 7 条）

> 结论先行：**业务 chunk 从 1.27 MB 降到 63 kB**、`StatCards` 从 570 kB 降到 2.45 kB；
> 但**首屏总字节基本持平**（-1.7 kB）——因为 Element Plus 本身就接近 1 MB 且外壳必须用它。
> 想要"首屏真的变小"，得改成按需引入组件（需要新依赖 or 大量 import 改写），**本期不做、已登记**。

## 1. 改了什么

只改 `frontend/vite.config.ts` 的 `build.rollupOptions.output.manualChunks`：把三方重依赖
按包名分到独立 chunk，**不改任何业务代码、不改 import 方式、不引入依赖**。路由级懒加载本来就
已经存在（`src/router/index.ts` 里 17 处 `() => import(...)`），本次不重复造。

```ts
manualChunks(id) {
  if (!id.includes('node_modules')) return undefined        // 业务代码不进 vendor
  if (id.includes('echarts') || id.includes('zrender')) return 'vendor-echarts'
  if (id.includes('element-plus') || id.includes('@element-plus')) return 'vendor-element-plus'
  if (id.includes('/vue/') || id.includes('vue-router') || id.includes('pinia') || id.includes('@vue/')) return 'vendor-vue'
  return undefined                                          // 其余三方交给 Rollup 按引用落位
}
```

**最后一行的 `undefined` 是踩过坑之后的结论**：第一版把"其它 node_modules"也塞进一个
`vendor` chunk，结果只有懒加载页才用的 `markdown-it`/`axios` 被提到首屏预加载集合里，
首屏反而**变大**了。**只拆已知重依赖，其余交给 Rollup**。

## 3. 怎么理解这组数字（别过度解读）

**真实收益**：
1. **缓存粒度**：改一行业务代码只会让 63 kB 的业务 chunk 失效，用户不必重新下载 1.27 MB
   （拆分前业务代码与 Element Plus 混在一个文件里，这是最伤的一环）。
2. **`StatCards` 570 kB → 2.45 kB**：图表库被挪出组件；不打开图表页就不会拉 `vendor-echarts`。
3. 三方库升级才会让 vendor chunk 变化，业务迭代与依赖升级的缓存互不干扰。

**没有收益的部分（如实说）**：
- **首屏总字节几乎不变**（-1.74 kB）。Element Plus 是外壳必需的 ~1.09 MB，拆分不减少字节数。
- **总字节**基本不变（-19.1 kB），分包不是压缩。

## 4. 后续（登记，不在本期）

要让首屏**真的**变小，只有两条路：
1. Element Plus **按需引入**（`unplugin-vue-components` + `unplugin-auto-import`）——**需要新依赖**，
   本期明确不允许；
2. 手写按组件 import（`import { ElTable } from 'element-plus'`）——改动面覆盖几乎所有页面，
   属于业务代码改写，风险与收益都不适合塞进"工程收尾"。
