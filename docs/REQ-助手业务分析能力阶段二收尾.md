# 需求文档：业务分析助手「阶段二收尾」——多 Tool / 受约束 Agent / 业务分析

> 版本：v1.0（2026-09-29）
> 上游：`docs/REQ-系统管理助手能力.md`（系统域一期只读 / 二期写操作，均已交付）
> 相关：`docs/DEC-助手按维度看订单分布.md`、`docs/DEC-助手回答的可见性与口径呈现.md`
> 一句话：把"助手能查数"提升为"助手能**稳定地**做业务分析"，并把它变成**可验收**的能力。

## 1. 背景与问题

### 1.1 现状：阶段一完成，阶段二主体已成

| 能力 | 现状（可核对） |
|---|---|
| 真实业务数据 | MySQL 20 张表；`tender_order` 100,000 + `performance_order` 50,000 单，`enterprise` 3,000，`project` 5,000，`sys_org` 21，`insurance_type` 6 |
| AI Chat | `POST /api/ai/chat` SSE（`meta/delta/reset/tool_call/proposal/proposal_result/done/error`）；会话与消息落库；历史窗口 20 条；相对时间语义解析 |
| Tool Calling | **16 个工具**：11 只读 + 5 写提案；按权限裁剪注册；调用明细落库（入参/结果/耗时/状态） |
| 可信性（2026-09-29 落地） | 口径行与提案编号已**上收服务端**：`TurnFacts` 在工具调用咽喉点采集真实 `dataSource`/`proposalNo`，收尾时服务端生成口径页脚（`DataSourceClaimGuard.footer`）并按白名单校验正文编号（`ProposalNumberGuard`）；模型自写的口径行与假编号一律被移除。这是 REQ-BA-09「表达规范」的事实基础 |
| 业务分析 | 订单汇总（量/保额/保费/企业数/项目数）+ 区域/机构/险种三维分布；页面上另有数据概览 4 图 12 卡 |
| 人工确认 + 审计（阶段四提前交付） | 提案 → 确认卡 → 执行 → 审计；`ai_operation_audit` 按月分区 + 90 天护栏 + 归档；脱敏；审计页与自查工具 |

### 1.2 问题：还差"稳定 + 完整 + 可验收"三件事

**问题 A：维度不完整，交叉维度答不了。**
`queryOrderDistribution` 只接受 `dimension/orderType/日期`，不接受 `regionCode/orgId`，因此
「**浙江省**各险种的结构变化」这类问题仍然答不了。
（技术事实：`criteriaFilter` 是四个分布查询**共用**的过滤片段，`regionCode/orgId` 早就支持——
只是工具入参没暴露，**加参数不需要写 SQL**。）

**问题 B：没有趋势工具。**
分析模块已有 `OrderAnalysisService.trend()`（`/api/analysis/order-trend`，支持按日/月/年粒度，
2026-09-29 刚修好粒度开关），但**没有对应的 AI 工具**："保费趋势如何"目前只能两两区间对比。

**问题 C：企业 / 项目维度缺失。**
业务侧三大主体是 订单 / 项目 / 企业，助手只覆盖了订单。问「哪些行业的企业下单最多」
「哪类项目占用担保额最高」目前无法回答。
（技术事实：分析模块的 `EnterpriseMapper` / `ProjectMapper` **只有分页与明细**，
没有按行业/等级/地区/项目类型的聚合查询——这是本阶段**唯一**需要新增 SQL 的地方。）

**问题 D：可靠性与成本没有护栏，也没有验收基线。**
真机数据（`ai_conversation` / `ai_tool_call` 实测）：

| 会话 | 调用次数 | 工具耗时合计 | 会话总耗时 | 结果 |
|---|---|---|---|---|
| 修复前 · 蛮力枚举 | 36 | 0.97 s | 22 s | 有时成功（34 次汇总调用，机构只枚举到省级，且险种取不到）／有时**一个字都没有** |
| 修复后 · 专用工具 | 8 | 0.76 s | 11 s | 三维度齐全 |

结论有两条，直接决定本阶段的技术路线：
1. **耗时几乎全在模型往返**（工具执行 < 1 s），所以延迟杠杆是"**减少轮次与调用数**"，不是优化 SQL；
2. 助手目前**没有**调用数上限、单次工具超时、整体超时，也**没有**"哪些问题应当答、哪些应当拒"的验收清单。

### 1.3 本需求的目标（阶段二完成的定义 DoD）

> **多 Tool**：业务分析工具覆盖 订单汇总 / 分布（含交叉过滤）/ 趋势 / 企业 / 项目 五个面；
> **业务分析**：黄金问题集 15 条全部达标（含 3 条"应当如实拒绝"的越界问题）；
> **受约束 Agent**：预算与降级可判定——轮次 ≤ 4、单轮调用 ≤ 12、整体 ≤ 60 s，
> 任何受限情形都必须给出**可读结论或可读原因**，绝不留空气泡。

## 2. 范围

### 2.1 In Scope

1. 分布工具支持交叉过滤（区域 / 机构）；
2. 新增趋势工具；
3. 新增企业维度、项目维度分析（含**新增聚合 SQL**）；
4. 新工具的统一契约（口径行 / 截断 / 条数归一 / 可读错误）；
5. 查询预算与超时护栏；失败与"缺维度"的降级话术；
6. 分析表达规范（环比/同比/占比/集中度的定义；结论与推测分离）；
7. 黄金问题集 + 真机冒烟脚本（阶段五 Evaluation 的雏形）；
8. 每次分析的**轮次 / 调用数 / token / 耗时**可观测（一条结构化日志 + 落库）。

### 2.2 Out of Scope（本阶段明确不做）

| 不做 | 原因 |
|---|---|
| RAG / 向量库 / 业务文档问答 | 属阶段三；业务知识目前由系统提示词承载（216 行），本阶段只做"工具能力" |
| MCP Server / Evaluation 平台 / Prometheus-OTel | 属阶段五 |
| 自主多步规划型 Agent（自己拆任务、自己决定查几轮、自主重试多次） | 见 §2.3 红线；本阶段只做**受约束**的多步执行 |
| 明细导出（把 15 万条订单给模型/导出 Excel） | 模型不该看明细，且与"工具返回值 16 KB 上限"冲突 |
| 图表渲染（ECharts 出图） | 现有 Markdown 表格已满足；作为 P2 可选（Q-BA-02） |
| 跨会话长期记忆 / 用户画像 | 属后续阶段 |

### 2.3 红线（不因本需求放松）

1. **模型不直接改数据**：写操作一律走"提案 → 人工确认 → 执行 → 审计"（既有机制，不动）。
2. **不生成 SQL、不注入 Mapper**：新增工具一律 `Tool → Service → Mapper`（与 `OrderSummaryTool` 同构）。
3. **不新增权限码、不改变既有权限口径**：新工具权限与"同类既有工具"一致（见 §5.1.6）。
4. **不返回明细全表**：任何工具都必须有 `limit` 归一与 `truncated` 标记。
5. **口径只有一个来源**：助手看到的分布/趋势必须与页面（数据概览）**同 Service、同 SQL**，不得另写一套。

## 3. 术语与角色

| 术语 | 含义 |
|---|---|
| 维度 | 订单的分组轴：区域 / 机构 / 险种（本阶段新增 企业 / 项目 / 时间） |
| 交叉过滤 | 切一个维度时同时带过滤条件（例：`dimension=INSURANCE` + `regionCode=330000` = 浙江省的险种结构） |
| 口径行 | 回答末尾 `口径：<dataSource>`。**已上收服务端**：服务端在收尾时用本轮工具返回值逐条生成（`DataSourceClaimGuard.footer`），模型自写的口径行会被剥离（`stripDataSourceLines`） |
| 预算 | 一次问答允许的模型轮次、单轮调用数、总时长、返回条数 |
| 收口轮 | 轮次用尽后摘掉工具、强制模型给结论的那一轮（已实现） |
| 黄金问题集 | 一组固定问题 + 期望口径/期望拒答的验收基线 |

| 角色 | 关注点 |
|---|---|
| 运营 / 只读用户（如"行政部的张涛"） | 能不能查到、数字对不对、口径说不说得清 |
| 数据分析师 | 多维对比、趋势、Top-N、集中度 |
| 管理员 / 审计 | 权限口径一致、每次分析可回溯（谁问了什么、调了什么、花了多少） |

## 5. 功能需求

### 5.1 工具补齐

#### 5.1.1 REQ-BA-01 分布工具支持交叉过滤（P0）

| 项 | 内容 |
|---|---|
| 变更 | `queryOrderDistribution` 增加两个**可选**参数：`regionCode`、`orgId` |
| 语义 | "先用过滤条件缩小范围，再按 dimension 分组"；一次调用仍只切**一个**维度 |
| 样例 | `dimension=INSURANCE, regionCode=330000, startDate=2026-04-01…` → 浙江省各险种 |
| 实现 | `AnalysisCriteria` 已支持这两个字段，四个分布查询共用 `criteriaFilter` → **无需新 SQL** |
| 口径行 | 追加 `区域：330000（浙江省）` / `机构：2`（沿用 `DataSourceText` 既有键） |
| 边界 | 区域用**层级前缀**匹配（选省 = 含其全部市/区县，与订单列表同口径），需在工具描述里写明 |

#### 5.1.2 REQ-BA-02 趋势工具 `queryOrderTrend`（P0）

| 项 | 内容 |
|---|---|
| 入参 | `orderType`、`startDate`、`endDate`、`granularity=DAY|MONTH|YEAR`（默认 MONTH）、`regionCode`、`orgId`、`limit` |
| 出参 | `points[{period, orderCount, guaranteeAmount, premiumAmount}]` + `meta`（口径行 / truncated） |
| 实现 | 直接复用 `OrderAnalysisService.trend(OrderTrendQuery)`（**零新 SQL**）；粒度归一化沿用本周修复的 `Granularity.normalize`（大小写不敏感 + day/month/year） |
| 条数 | 默认 24 个点、上限 120；超出时**从最近端截断**并在 `truncated` 里说明"只给了最近 N 个周期" |
| 描述要点 | 明确"趋势/拐点/逐月变化"用它；"两个区间比大小"用汇总或分布工具 |
| 风险 | 日粒度跨 21 个月 ≈ 640 个点 → 必须走 `limit` + 截断提示，避免 16 KB 上限触发 |

#### 5.1.3 REQ-BA-03 企业维度（P1）

| 项 | 内容 |
|---|---|
| 形态 | `queryEnterpriseAnalysis(mode=DISTRIBUTION|TOP, dimension=INDUSTRY|LEVEL|REGION, orderType, 日期, limit)` |
| DISTRIBUTION | 按行业 / 等级 / 地区聚合**企业数**，并附该组下的订单量、保额、保费（join 订单聚合） |
| TOP | 按订单量或保额倒序的**企业排行**（企业名 + 编码 + 订单量 + 保额 + 保费） |
| 数据来源 | **新增 2 条聚合 SQL**（`tender_order ∪ performance_order` 按 `enterprise_id` 聚合，再 join `enterprise` 取名称/行业/等级） |
| 索引依据 | `idx_tender_enterprise` / `idx_perf_enterprise` 已存在；150k 行规模下聚合为毫秒级 |
| 口径注意 | 企业名称必须"历史保留"：join `enterprise` **不带** `is_deleted/status` 条件（见 `DEC-订单筛选下拉的选项口径.md` §2.4） |

#### 5.1.4 REQ-BA-04 项目维度（P1）

| 项 | 内容 |
|---|---|
| 形态 | `queryProjectAnalysis(mode=DISTRIBUTION|TOP, dimension=PROJECT_TYPE|REGION, orderType, 日期, limit)` |
| DISTRIBUTION | 按项目类型（房建/市政/交通/水利/其他）或地区聚合项目数与订单指标 |
| TOP | 按担保金额倒序的**项目排行**（项目名 + 编码 + 金额 + 保函额 + 保费） |
| 数据来源 | **新增 2 条聚合 SQL**（同上思路，按 `project_id` 聚合 + join `project`） |
| 索引依据 | `idx_tender_project` / `idx_perf_project` 已存在 |
| 口径注意 | 项目类型是**中文枚举**（与项目管理页一致），返回值直接给中文，不要让模型翻译 |

#### 5.1.5 REQ-BA-05 新工具统一契约（P0，写进代码评审清单）

每个新工具**必须**满足（前四条已在既有工具里成型，这里固化为"新工具准入条件"）：

1. 返回 `record`，且 `meta` 用 `ToolResultMeta`（`denied` / `truncated` / `dataSource`）；
2. `dataSource` 走 `DataSourceText`，**不含**工具名与英文参数名；
3. `limit` 归一（默认值 + 硬上限），截断必须显式标记；
4. 参数非法给**可读中文错误**（如"日期必须是 yyyy-MM-dd"），不抛堆栈给模型；
5. 只依赖 Service，不注入 Mapper；
6. 有单测（字段映射 / 边界 / 口径文本）+ 至少 1 条真实库 IT（与页面同 Service 逐字段一致）。

> **第 4 条的落地口径（2026-09-30 定稿，消除与"枚举回落"的张力）**：枚举类参数（如 `granularity`）
> 的非法值**按既有 `normalize` 静默回落**到默认档（与数据概览页同一行为，不报错），
> 但**必须在返回值里回显归一化后的生效值**（`OrderTrendToolResult.granularity` 已如此），
> 使模型能如实告诉用户"实际用的是哪一档"。其余参数（日期格式、维度取值、条数）仍按第 4 条报可读错误——
> 它们的非法值没有"合理默认"，静默回落会让用户拿到错误范围的数据。

#### 5.1.6 权限口径（沿用既有判断，不新增权限码）

| 工具族 | 权限 | 依据 |
|---|---|---|
| 订单汇总 / 分布 / 趋势 | 不额外要求（登录 + `ai:chat`） | 与 `queryOrderSummary` 一致；页面侧 `/api/analysis/**` 亦只要求登录 |
| 企业分析 | 不额外要求，或与 `enterprise:view` 对齐（**Q-BA-03 待定**） | 企业页要求 `enterprise:view`；但订单侧已是开放口径，混用会造成新的不一致 |
| 项目分析 | 同上（`project:view`） | 同上 |

> 本阶段**不**借机收紧或放宽任何权限；`/api/orders/**`、`/api/analysis/**` 的鉴权缺口是既有未决项。

### 5.2 受约束 Agent（预算 / 降级 / 收口）

#### 5.2.1 REQ-BA-06 查询预算与超时护栏（P0）

| 预算项 | 现值 | 目标 | 触顶行为 |
|---|---|---|---|
| 模型轮次 | 4（已有收口轮） | 4（不变） | 进入收口轮（已实现），必须产出结论 |
| **单轮工具调用数** | 无限制（真机出现过 30 次/轮） | **≤ 12** | 超出部分不执行，回灌一条"本轮调用过多，已截断"的工具结果，让模型下一轮补查 |
| **整体时长软超时** | 仅 Servlet 5 min | **60 s** | 停止取数 → 进入收口轮（用已有数据作答） |
| 单次工具执行 | 无 | **10 s** | 该工具记为 FAILED，模型得到可读失败原因 |
| 工具返回大小 | 16 KB（`BoundedToolCallback`） | 不变 | 已实现截断标记 |

> 依据：真机 8 次调用 = 11 s、36 次调用 = 22 s，工具合计 < 1 s → 时长几乎等于"轮次 × 单轮模型耗时"，
> 因此 60 s 软超时对正常问答无感，只在异常放大时兜底。

#### 5.2.2 REQ-BA-07 先列计划再取数（P0，仅提示词层）

要求模型在**首次**调用工具前，用 1~2 句说明"要查哪几个维度/区间"，然后**在一轮内把该查的一次查齐**。
- 目的：把"逐个小步试错"变成"一次问全"，直接对应延迟与轮次；
- 约束：**不新增 SSE 事件、不改协议**（这句话会随 `delta` 正常流式显示，符合现有交互）；
- 验收：黄金问题集里"三维度对比"的调用轮次 ≤ 3。

#### 5.2.3 REQ-BA-08 失败与缺维度的降级（P0）

| 情形 | 必须说的话 |
|---|---|
| 工具失败 / 超时 | 哪个指标没取到、原因（可读）、哪些结论因此不成立 |
| 无权限（工具未注册） | 「你的账号没有 XX 权限」，不暗示"系统不支持" |
| 数据为空 | 「该条件下 0 条」，并给出相邻口径（放宽区间/换维度）的建议 |
| 问题超出工具能力 | 明确说"当前查不了 X"，并给**1~2 个可执行的替代问法**（例："可以改成问某个区域的险种结构"） |
| 明细被截断 | 必须说明"只看过前 N 名/最近 N 个周期"，不得说成"全部" |

#### 5.2.4 REQ-BA-09 分析表达规范（P1）

1. **环比** = 本期 vs 上一相邻等长区间；**同比** = vs 去年同期；**占比** = 该组 / 同期总量——三者必须在正文里写明用的是哪个；
2. **结论与推测分离**：推测段必须以「以下为推测」开头（真机已自发做到，纳入验收）；
3. **集中度**只在给出分子分母时使用（例："浙江+江苏占 60.07%"）；
4. 金额统一"元（两位小数）"，必要时附"亿元"并标单位；
5. 口径行**不要自己写**：已上收服务端（收尾时按本轮真实工具返回值逐条追加）。
   模型若仍写出口径行会被剥离；正文里需要说明条件时用**人话**（"险种：投标保函""2026-04-01 ~ 2026-06-30"）。

#### 5.2.5 REQ-BA-10 越界拒绝清单（P0）

| 用户可能问 | 助手必须 |
|---|---|
