## 3. 核心设计决策

> **⚠ 本节决策 1、2 已被推翻**（2026-09-22 评审指出"机构与部门混在一起"）。
> 保留原文仅为记录决策过程，**最终形态以 §14 为准**：机构不是部门树的一层。
> 决策 3（必须去掉分页）、决策 4（保留祖先链）**仍然有效**。

### 决策 1：树的"根"是什么

部门层级是**机构内**的（`parent_id` 只在同一 `org_id` 内有效，后端已强制）。而"所属机构"下拉默认是**全部机构**。于是"全部机构"视图下有 **21 个根节点**，且它们之间没有任何父子关系。

| 方案 | 全部机构视图 | 选中单机构 | 评价 |
| --- | --- | --- | --- |
| **A. 机构为顶级节点**（推荐） | `机构(21) → 部门(21) → 子部门(59)`，三级 | `部门(1) → 子部门(3)`，两级 | 天然表达"部门属于哪个机构"；跨机构不会误读父子关系；与"21 个根"的视觉噪音问题一起解决 |
| B. 只展开部门层级 | 平铺 `部门(21) → 子部门(59)`，21 个根并列 | 同左 | 改动最小，但"全部机构"下看不出一棵树，只是 21 棵两级的树拼在一起 |

> **推荐 A**，理由：现有页面本来就依赖"所属机构"下拉来定位（21 项平铺下拉里找机构很费劲），A 顺带把这个定位动作变成"在树上点"，可以省掉下拉的默认操作。

### 决策 2：概览节点（机构行）的语义边界

方案 A 引入的**机构行不是部门**，必须严格区分，否则行为会出错：

| 维度 | 部门行 | 机构行（概览） |
| --- | --- | --- |
| 数据来源 | `sys_department` | `sys_org`（`org_id` 聚合） |
| 状态标签 | 显示（1 启用 / 0 停用） | **不显示**（机构状态与部门状态是两回事，别混） |
| 操作按钮 | 删除 / 恢复 | **不渲染任何操作**；无权限/无部门时显示 `--` |
| `id` | 部门真实 id | **必须与部门 id 不撞号**：推荐 `rowKey` 用**字符串** `"dept-<id>"` / `"org-<id>"`（`el-table` 的 `:row-key` 支持返回字符串），最直观且无算术风险；若坚持用数字，则机构行取 `-orgId`，需在注释里写明 |
| 子节点为空 | —— | 显示为叶子（不显示展开箭头） |

`row-key` 冲突是这类"两套实体拼一棵树"最容易踩的坑：机构 id=1 与部门 id=1 同时存在，Element Plus 会把它们当成同一个节点。

### 决策 3：分页必须去掉

树形**不能**分页（SYS-C-24）：

- 保留 `pageSize=10` → 树只有 10 个节点，第 11 个部门消失，**且界面看不出异常**；
- 保留分页但把 `pageSize` 调大 → 换汤不换药，数据一多就再犯；
- 正确做法：**新增全量接口**，树一次取全，服务端设条数上限 + 超限告警（与机构树 `TREE_LIMIT = 2000` 同构）。

代价：部门总数失去"分页总数"这个来源，改为客户端统计（`共 N 个部门 / 涉及 M 个机构`，由树数据直接算出，更直观）。

### 决策 4：筛选语义——保留祖先链

与机构树完全一致（SYS-C-19）：

- **服务端**：`orgId`（点击机构行/下拉选择时下发）、`deptName`、`deptCode`、`status`、`includeDeleted`；
- **客户端**：按关键词过滤时，必须把命中节点的**整条祖先链**补进来，否则 Element Plus 会把子部门当根节点挂到顶层，出现"游离节点"；
- **分组节点特例**：机构行没有"状态"属性。若只按状态过滤（如只看停用），机构行不能因此消失——**只要它下面还有命中节点就保留**，并显示 `停用 2/4` 之类的命中计数，而不是简单隐藏。

## 4. 接口设计

### 4.1 新增（唯一需要新增的接口）

```
GET /api/system/departments/tree
权限：system:dept:view（includeDeleted=true 时额外要求 system:dept:delete，与列表接口同规则）
入参：orgId? / deptName? / deptCode? / keyword? / status? / includeDeleted?
出参：Result<List<DepartmentVO>>   ← 扁平全量列表，非嵌套
```

三点说明：

1. **必须复用列表的口径**：新增 `selectTree` 时 `<include refid="queryWhere"/>`，保证"树上看到的 = 列表能查到的"。若另写一套 WHERE，就会出现"列表有、树上没有"这类最难查的不一致。
2. **`includeDeleted` 的参数级鉴权不能漏**：否则可绕过列表的 `@PreAuthorize` 从树接口读到已删除部门（机构树当初就是靠 `requireDeletePermissionWhenIncludingDeleted` 补上的）。
3. **返回扁平列表而不是嵌套**：与 `GET /api/system/orgs/tree` 保持一致，也让"祖先链补全"这类客户端逻辑更简单（先生成 `Map<id, node>` 再挂 children）。

### 4.2 后端改动清单

| 文件 | 改动 | 量级 |
| --- | --- | --- |
| `DepartmentController.java` | 新增 `GET /tree`，带 `@PreAuthorize(DEPT_VIEW)` + `requireDeletePermissionWhenIncludingDeleted` | +12 行 |
| `DepartmentService.java` | 新增 `tree(query, scope)`：注入 scope → `selectTree` → 上限告警 | +15 行 |
| `DepartmentDto.java` | 新增 `TREE_LIMIT = 2000` 常量（或用 `PageQuery` 的既有上限） | +1 行 |
| `SysDepartmentMapper.java` | 新增 `selectTree(@Param("q") Query, @Param("limit") int)` | +3 行 |
| `SysDepartmentMapper.xml` | 新增 `selectTree`：`voCols` + `fromJoin` + `queryWhere` + `ORDER BY d.org_id, d.sort_no, d.id` + `LIMIT` | +8 行 |
| VO | **不用改**——`DepartmentVO` 已含 `parentId` / `orgId` / `orgName` | 0 |

**不需要**的：新权限码、新表、新字段、迁移脚本、`DataInitializer` 改动。

> 现实评估：80 条部门按 `org_id` 排序返回，对这个体量没有任何性能问题；`TREE_LIMIT` 是防御性上限，不是当前需要。

### 4.3 保持不变（兼容性红线）

| 保留项 | 原因 |
| --- | --- |
| `GET /api/system/departments` 分页接口 + `PageResult` 结构 | 助手侧 `queryDepartment` 工具（SYS-Q-02）在用；改结构会连带改工具与测试 |
| `GET /departments/options` | 用户页/其它下拉在用 |
| `DELETE` / `POST /{id}/restore` | 逻辑删除链路不变 |
| `DepartmentVO` 字段 | 树复用同一 VO |

## 5. 前端改造

### 5.1 组件与函数

| 位置 | 改动 |
| --- | --- |
| `api/system.ts` | 新增 `listDepartmentTree(params)` |
| `types/system.ts` | 新增 `DepartmentTreeNode`（含 `children`、`nodeKind: 'ORG' \| 'DEPT'`、`selfDeleted`、`childStats`） |
| `Departments.vue` | 见下 |

### 5.2 树组件选型：沿用 `el-table`（`row-key` + `tree-props`）

| 选项 | 取舍 |
| --- | --- |
| **`el-table` + `tree-props`**（推荐） | 保留现有全部列与"删除/恢复"列；与 `Orgs.vue` 写法一致；后续加"新增下级/修改/启停"按钮是加列，不动结构 |
| `el-tree` | 层级更醒目，但**没有列**——编码、状态、排序、操作都要塞进节点文本，信息密度反而下降；且 `Orgs.vue` 用的就是 `el-table`，两页会不一致 |

### 5.3 列调整

| 列 | 处理 | 理由 |
| --- | --- | --- |
| `上级部门ID`（裸数字） | **删除** | 树形已经把父子关系可视化了，再放一列 `parent=1` 是噪音 |
| 其它列 | 保留 | —— |
| **新增** `层级路径`（可选） | `平台总部 / 业务受理部`，`show-overflow-tooltip` | 过滤命中后祖先链被自动展开，路径列能直接说明"它是谁的子部门" |
| **新增** 机构行的 `部门数` | 机构行显示 `4 个部门` | 概览信息，替代原来的分页总数 |

列的渲染需要按 `nodeKind` 分支：机构行只在"部门名称"列显示机构名（加粗/不同底色），其余列显示 `--`。

### 5.4 交互

| 交互 | 行为 |
| --- | --- |
| 默认展开 | 展开机构层 + 顶级部门（数据只有两级，等于默认全展开）；`expandedKeys` 受控 |
| 展开/收起 | 行首箭头；`handleShowDeletedChange` / 机构切换 / 重置 时清空 `expandedKeys` 重新默认展开（已删除节点可能藏在折叠层里） |
| 点击机构行 | 视为"只看该机构"（等价于选中下拉），并刷新；再次点击取消 |
| 删除 | 确认弹窗保留现文案；**树形下补一句**"有下级部门的不能删除"（后端会拒绝，提前说明减少无效操作） |
| 恢复 | 树形下更适合操作：恢复后节点归位；失败提示"请先恢复其上级部门"照旧 |
| 空态 | `el-empty`（保留） |

### 5.5 筛选后的祖先链（复用 `Orgs.vue` 的算法）

```
1. 遍历全量节点，按 keyword / status / orgId 计算 matched 集合
2. 把 matched 中每个节点的祖先全部加入 visible 集合
3. 机构分组节点：其下只要有 visible 子节点就保留
4. 按 visible 组树；父不在 visible 内的节点提升为根（防游离）
5. 排序：nodeKind(ORG 先) → sortNo → id
6. 命中数 > 50 时给出提示（与机构树一致的阈值）
```

## 14. 设计纠正：机构不是部门树的一层（2026-09-22，评审指出）

### 14.1 错在哪

**评审原话**：「部门是部门机构是机构，部门和机构怎么混到一起去了，机构是出函的机构，部门是公司内部的部门」。

原 §3 决策 1 选的**方案 A（机构为顶级节点）是错的**，它把两个不同实体混进了一棵树：

| 实体 | 表 | 层级来源 | 层级含义 |
| --- | --- | --- | --- |
| 机构（出函机构） | `sys_org` | `parent_id` + `org_level` | 总部 → 省级 → 市级，**业务主体**的行政区划层级 |
| 部门（公司内部部门） | `sys_department` | `parent_id` | 公司内部组织层级，**归属**某个机构 |

`sys_department.org_id` 只是部门的一个**归属属性**。把它提升成树的层级会同时造成两个错误：

1. **机构在树上的位置是虚的**——它根本不是任何部门的父节点（`parent_id` 指向的永远是另一个部门），
   这一层纯属人造成因，还会让人误以为"机构的上下级关系"和"部门的上下级关系"是同一种关系；
2. **部门真实的父子层级被压成平级**——本项目数据是"每机构 1 个顶级部门、其余挂它下面"（SYS-P-18/P-25 特意构造），
   方案 A 把这 4 个部门显示成同层的兄弟，等于把要展示的层级本身给抹掉了。

### 14.2 纠正后的形态

**树只由 `sys_department.parent_id` 构成；机构只以"归属属性"出现：**

| 出现形式 | 位置 |
| --- | --- |
| 筛选条件 | 筛选区「所属机构」下拉（`orgId` 参数，服务端过滤） |
| 「所属机构」列 | 每行显示该部门归属的出函机构 |
| 根节点上的机构标签 | **仅顶级部门**（`parent_id = 0`）这一行挂一个机构名标签，点击=只看该机构；子部门不重复（从父节点一眼可见） |

结果：**21 棵部门树并排**（21 个机构各 1 个顶级部门，共 21 个根节点 + 59 个子部门），
每个根节点都带机构标签，因此"这棵树属于哪个机构"依然一眼可见，但**不是**靠伪造的树层级来表达。

### 14.3 连带修改

| 项 | 变化 |
| --- | --- |
| `DepartmentTreeNode.nodeKind` | `'ORG' \| 'DEPT'` → **`'DEPT'`**（类型上直接表达"本树只含部门"）；`childStats` 字段删除 |
| `treeData` 组装 | 删除"按 org 分桶 + 造机构节点"整段；根 = `parent_id = 0` 或父不在可见集合；根按归属机构成块排序（便于"全部机构"视图阅读） |
| 首列 | 机构行分支删除；改为「部门名称 + 顶级行的机构标签」 |
| 操作列 | 机构行分支删除（不再有机构行 → 不再需要"机构行只提供新增部门"） |
| 筛选 | 「所属机构」下拉保留（本来就是正确形态），无需改动 |
| 新增部门入口 | 工具栏「新增部门」需先选定机构（或走某行的「新增下级」）；逻辑不变 |
| 后端 | **零改动**——`/tree` 返回的一直是扁平部门列表，机构层级是前端造出来的 |

### 14.4 验收（`scripts/verify-dept-tree-shape.mjs`，10 项全通过）

## 15. 部门树与人员归属重构（2026-09-22，评审要求）

├── 业务部 ── 杭州部 / 台州部 / 温州部

├── 人事部
├── 行政部

### 15.3 迁移过程中的三次失败与教训（都值得记住）

| # | 现象 | 根因 | 教训 |
| --- | --- | --- | --- |
| 1 | 迁移"执行成功"但部门数没变 | `mysql --execute="... SOURCE f.sql"` 不解析客户端命令，整串被按 `;` 拆开逐条发送；且我把 stderr 丢进了 `$null` | **不要把报错静默掉**；脚本用标准输入喂给 mysql |
| 2 | **部门表被删空、300 个用户 dept_id 全空** | 校验写成裸 SQL 里的 `SIGNAL`（那是存储程序语法，裸 SQL 非法），于是"删除执行了、插入没执行" | 破坏性操作前必须有**能被独立执行**的校验；已改为运行器在删除前用独立查询判定，失败即中止 |
| 3 | `Can't reopen table: 'm'` | MySQL **TEMPORARY 表不能在同一语句里被引用两次** | 映射表用普通表；这类限制要么先查文档，要么先在临时库上试 |

第 2 次靠 `mysqldump` 全库备份完整恢复（部门 80、用户 300、订单 10 万+5 万全部回位）。
迁移脚本因此固化为：**默认只演练**，`-Apply` 才写库且先自动全库备份，阶段 2 之前做映射校验。

### 16.2 连带后果与处理（重要）

**数据范围的演示数据没了。** 原先设计让 `operator` 属省级、`analyst` 属市级，
好让"省级只看本省 / 市级只看本市"能在演示账号上直接看到。所有人改挂总部后，
这三个账号的可见范围与 `admin` 相同（都是全量）。

处理方式：**没有降低覆盖，而是把这块覆盖搬到夹具上**。
`DataScopeIntegrationTest` 新增 `ScopeFixture`：自建"夹具总部 → 夹具省一（含 2 市）／夹具省二（含 1 市）"
共 6 个机构 + 2 个用户，用完物理删除。于是以下断言依旧成立且更精确：

| 断言 | 说明 |
| --- | --- |
| 省级范围 = 自身 + 本省 2 市（共 3 个机构） | 且**跨省的市不可见**——这是最容易漏的穿透点 |
| 市级范围 = 仅本市（`isSingleOrg`） | 且**同省的另一个市不可见** |
| 跨范围查询返回 0 条 | 查同省另一个市的名称，表现为"不存在"（SYS-P-09 不暴露存在性） |
| 省级看不到其上级（总部） | 范围是"自身 + 下级"，不含父级 |

这样反而比依赖演示数据更稳：演示数据以后再怎么改，安全边界的测试都不会跟着失效。

### 16.3 一个必须记住的入口差异

**`DataInitializer` 仍然按"21 个机构各一棵 11 个部门的树"生成演示数据**，与当前库不一致。

- 原因：`DataInitializer` 是**全量演示数据的源头**（含 21 个机构的三级层级、地区分布、订单等），
  它的部门树是配合 21 机构设计的；只把部门改成单机构会让"每个机构都有部门"等其他演示语义一起破掉。
- 影响：若执行 `scripts/reset-demo-data.ps1` 清库重灌，部门会回到 231 个（21 棵）；再跑一次
  `migrate-dept-single-org.ps1 -Apply` 即可回到当前状态。
- 之所以不做成"初始就是单机构"：那会连带删掉 20 个机构或让它们没有部门，
  是另一个更重的改动，应单独决策（已记录在此，未擅自实施）。
